# WGSL / CUDA / PBB 优化对照（2026-11-23）

## 结论先行

- 在同一张 RTX 5060 Ti、同一批 Base16384 名字、同一组 p550/x4000/d5000 条件下，CUDA 全链路比当前正式 WGSL **快约 29.45%（E2E）**，比工作区未提交的分段收集版本**快约 34.46%**。
- 本轮 CUDA E2E 中位数约 **7616 万名/秒**，折合理想满载约 **6.58 T/天、46.06 T/周**；正式 WGSL 中位数约 **5883 万名/秒**，约 **5.08 T/天、35.58 T/周**。
- 本轮起始工作区的 WGSL 分段 collect_base 比正式旧版慢约 **3.72%**。已有三轮十亿实测也给出分段版约 **-3.06%**，不建议把该工作区改动作为优化合入。
- PBB 是 CPU C++ 引擎，不是 CUDA 后端；它和 WGSL 目前也不是同一评分口径。PBB 的多级评分门控不能直接移植到当前 WGSL，而 PBB 的四路 KSA、SIMD 属性/技能压缩、前缀复用是值得继续借鉴的 CPU 优化。

## 正确性验证

独立 CUDA DLL 先做了完整捕获和筛选集合对拍：

- [0, 65537)：65,537 个候选，CUDA / WGSL / CPU 全字段一致，shadow 12,405。
- [2^32-17, 2^32+240)：257 个候选，覆盖 u32 进位。
- 从 u64::MAX-256 到 u64::MAX（含末端）：257 个候选，覆盖高位边界。
- [0, 32771)：非 capture 模式命中 2,170，CUDA / WGSL / CPU 筛选集合一致，shadow 4,068。
- CUDA f32 相对 CPU f64 的最大误差仍小于约定的 10 分余量；正式验证中最大 XP 误差约 0.0054，最大 XD 误差约 0.0536。

## CUDA 测试实现

窄化收集循环时，full 模式不能检查已收满 128 项再停：虽无语义差异，却曾将 CUDA 降至约 6586 万名/秒；恢复编译期全扫描后，两轮短测回到约 7611–7613 万名/秒。

新增文件：

- [cuda-mine.cu](../benchmarks/cuda-mine.cu)：独立 CUDA DLL；CUDA 对照不依赖更改 wgpu 生产内核。
- [cuda-ab 宿主](../examples/cuda-ab/main.rs)：通过 Rust FFI 调 DLL，复用现有 CPU 金标准、CSV 和 GPU host 验证。
- [build-cuda-ab.ps1](../benchmarks/build-cuda-ab.ps1)：用 nvcc + MSVC 构建，默认 sm_120。
- [measure-cuda-ab.ps1](../benchmarks/measure-cuda-ab.ps1)：固定输入、反向交替、哈希校验的正式复测脚本。

从 namerena-rs 根目录复现：

~~~powershell

$env:RUSTC_WRAPPER = ""

# 只做边界和全量对拍；--out 必须是新的目录
~~~

CUDA 当前有三个内核变体用于实验：split（先收 31 项）、full（一次收全量）和 sort10（固定比较网络）。正式结果采用与生产 WGSL 等价的 full32；短测中 sort10/32 相对 full32 只有约 0.3% 的端到端增益，低于本轮需要用长测判定的收益量级。

## WGSL 和 PBB 的优化差距

### WGSL 已经做好的部分

[测号 shader](../mining.wgsl) 已经有：

1. packed S-box：32 lane 共享存储从 32 KiB 降到 8 KiB；
2. GPU 直接从 u64 ID 生成 Base16384/Base64 名字；
3. 公共前缀 KSA 快照；
4. 保持 1034 项同源模型语义的非零特征压缩；
5. 批大小和工作组 A/B，当前机器的生产最优是 packed/32/524287。

### PBB 的 CPU 优化领先点

PBB 正式 CPU 路径主要集中在 [name.hpp](../../../PBB/source/pbb/native/src/name.hpp)、[utils.hpp](../../../PBB/source/pbb/native/src/utils.hpp) 和 [scoring_1124.hpp](../../../PBB/source/pbb/native/src/scoring_1124.hpp)：

- 四候选交错 KSA（batch width 4）以及固定前缀状态复用；
- AVX2/AVX-512 一次处理 32/64 字节的属性与技能过滤、压缩写入；
- V 值分三级早退，随后还有共享门、每评分族门和懒算多项式；
- 十个评分族、SP1/SP2 两套特征和 PTT 潜力上界按计划计算，any 模式还可以遇到达标族后短路。

这些是 CPU 版本的优势，但不能直接拿来和当前 WGSL 的两个 XP/XD 模型比较：PBB 默认配置启用十个评分族并包含潜力/特殊收集语义，而 WGSL 当前链路只复现 XP/XD 两个模型和相同的 p/x/d 过滤。要做公平比较，必须先定义相同的评分计划、输入枚举和输出语义。

### 当前 PBB 产物的注意点

当前 [settings/build_config.json](../../../PBB/settings/build_config.json) 仍是 tested: false / status: none。现有 [pbb_engine 构建清单](../../../PBB/source/build/pbb_engine.exe.build.json) 是 portable -march=x86-64 产物，且 build_config 为 null；它不是一次已确认的本机 native autotune 结果。也就是说，PBB 源码里写好的 KSA/SIMD 优化和发布目录里当前可执行文件的实际 ISA/编译选项不能混为一谈。本轮没有擅自安装 pybind11 或重建 PBB；尝试调用 Python 编排层时因缺少 pybind11 停止，因此这里只报告 PBB 的代码与构建差异，不报 PBB 的同机吞吐。

## 计时与比较边界

E2E 为初始化后完整扫描、回读、CPU 复核及 CSV flush，不含设备或管线创建、进程退出。T 为 10^12 个候选，日周值是 86400 秒和 604800 秒理想连续运行的外推；高命中任务仍可能受 CPU 与 CSV 写入限制。该试验对应本机仅有的 RTX 5060 Ti；多卡机器应先确认两个后端选择的是同一物理设备。E2E 的领先主要来自内核，但还包含两套宿主与回读路径差异，不能解释为任意 WGSL 程序换用 CUDA 都会有同等收益。

历史会话按引用 capturedThroughSeq=263 的用户/助手摘要核对，另外核对本地 250 亿候选 CSV 的 934 条记录；没有获取额外持久化快照。上次估算派发次数有误：25,000,000,000 / 524,287 向上取整为 47,684 批，不是 477 批。

## 下一步判断

1. **不要合入当前分段 collect_base 实验**：已有长测和当前三路复测都呈负收益。
2. **CUDA 路线有现实收益**：本机同口径约 +29% E2E；但它锁定 NVIDIA/CUDA，需另维护 CUDA kernel。
3. **WGSL 继续优化的优先级**：先做 shader 内核 profiling，再考虑 PBB 的 gate 思路；直接搬 PBB 十族 gate 不保证等价，且当前 p550 属性通过率约 66.53%，不是“绝大多数在属性门被淘汰”的场景。
4. **若要比较 PBB 本身**：先用 PBB native autotune 生成本机已验证产物，再用同一输入规模、同一输出策略和明确的评分计划单独测；不要用 PBB 默认十族输出速度直接宣称它比 WGSL 快或慢。
